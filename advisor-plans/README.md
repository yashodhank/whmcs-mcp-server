# MCP server/client intelligence architecture plans

Generated by the `improve` skill on 2026-08-07. These plans are written against
`main` commit `ebab2c5` and intentionally change no runtime code. Each executor
must run its drift check before implementation.

## Outcome

Evolve the server from a large collection of hand-wired MCP handlers into two
explicit planes:

```text
MCP clients
   │  2025 compatibility or 2026 stateless requests
   ▼
Protocol adapters ──► identity / policy context ──► tool catalog
                                                   │
                      CONTROL PLANE                ├─ capability evidence
                      manifest + PlanIR            ├─ safe plan compiler
                                                   └─ governance contracts
                                                           │
                                                           ▼
                      EXECUTION PLANE        domain handlers / workflows
                                                           │
                                               WHMCS request pipeline
                                                           │
                                           WHMCS External API
                                      or owner-transfer-only guarded
                                             DB write transaction
```

The control plane describes what can be done, under which policy, and at what
cost/risk. The execution plane performs only validated operations. The proposed
"brainstorming skill" lives on the host side and compiles operator goals into a
typed, non-executable `PlanIR`; it never becomes a second write path.

## Why this order

1. Pin observable behavior first. The server exposes roughly 70 tools and both
   legacy and governed output shapes; migration without contract fixtures would
   make regressions difficult to distinguish from deliberate protocol changes.
2. Adopt MCP `2026-07-28` through a compatibility adapter. The new protocol is
   stateless and the TypeScript SDK is split into server/client packages, while
   this repo still uses `@modelcontextprotocol/sdk` v1 and maintains per-session
   HTTP maps.
3. Establish one machine-readable catalog. Today registration, capability
   status, authorization annotations, prompts, resources, validation and docs
   are maintained through separate structures.
4. Refactor and accelerate the WHMCS data plane behind unchanged `read()` and
   `mutate()` contracts. This isolates retry, deadline, caching and telemetry
   policy from domain handlers.
5. Add intelligence only after capabilities and risks are queryable. The planner
   emits typed plans and draft intents; it does not call WHMCS mutations.

Plans 003 and 004 may run in parallel after 001 because their file ownership is
separate. Plan 005 should consume the catalog from 003. Plan 002 should land
before exposing modern-protocol-only UX such as MRTR, cache hints or Tasks.

## Architecture invariants

- A model-proposed plan is data, never authority.
- All mutations still pass the existing write intent state machine, execution
  gate, consumer scope checks, kill switch and `WhmcsClient.mutate()` backstop.
- Read policy executes before cache lookup. Cache and request coalescing never
  apply to writes or capability probes with side effects.
- Transport identity is authoritative and cannot be overridden by tool input.
- Governance projection remains the sole output boundary for governed data.
- The 2025-era stdio/HTTP behavior stays supported until the compatibility
  matrix and production clients prove it can be retired.
- Dynamic capability evidence is installation-scoped and expires; no global
  process cache may make one WHMCS installation describe another.
- Protocol and SDK migration must not be combined with handler rewrites.

## Global verification gate

Every implementation PR must run:

```bash
npm run precommit
npm run build
npm audit --audit-level=high
```

Plans 001 and 002 add MCP conformance/compatibility commands; later plans must
also run those commands. The opt-in live WHMCS stack remains supplemental and
must never be represented as having run unless `MCP_WHMCS_STACK=1` was actually
used against the disposable local stack.

## Global STOP conditions

- A change requires weakening consumer projection, write authorization, the
  kill switch, action allowlists, or the read-only mode.
- A proposed SDK API is not present in the installed stable v2 packages or its
  official migration guide. Stop and revise the plan instead of guessing.
- Legacy and modern protocol behavior cannot be tested independently.
- A catalog migration changes a tool name, schema, annotations or output shape
  without an explicit compatibility decision.
- Performance work makes a mutation retryable, cacheable or coalesced.
